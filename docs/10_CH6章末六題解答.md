# Hello Agents 第六章：六題章末題解答

> 對應《Hello Agents》V1.0.2，第六章 6.1–6.6。本文以繁體中文作答。框架 API 會演進；教材中的版本與下方「目前官方文件」需分開看。已執行的只有本專案 AutoGen、LangGraph 及獨立的 Pydantic 獵人規則範例；CAMEL Workforce 和 AgentScope 分散式方案是根據文件的設計，沒有冒稱實測。

## 1. 兩個框架的深入比較；湧現式協作與顯式控制

選擇 **AutoGen** 與 **LangGraph**，因為本專案有兩者可執行的案例。

| 維度 | AutoGen | LangGraph |
|---|---|---|
| 協作模式 | 把不同職責的 Agent 放進團隊，透過訊息接續工作。例如產品經理、工程師、審查員、QA 依序討論。同一框架可採輪詢、選擇發言者等團隊設計。 | 把工作定義為節點，把共享資料定義為 State，用邊連接步驟。多個 Agent 也可以各自成為節點或子圖，但核心可觀察物是狀態與流向。 |
| 控制方式 | RoundRobinGroupChat 是固定順序；若需求變更要立即回到產品經理，需改用具路由能力的團隊，例如 SelectorGroupChat 的 selector_func，或自行編排。控制規則由開發者設計。 | 普通邊固定轉移，條件邊依 State 決定回搜尋、回生成或結束。重試次數、品質門檻等可以明確寫在狀態和路由函式中。 |
| 適用場景 | 需要角色分工、討論、審查與多輪協作，例如軟體開發團隊。若角色只是互相說「完成」，仍需外部測試驗收。 | 步驟、分支、重試及人工審核必須清楚可追蹤的任務，例如檢索問答、測試修復循環與審批流程。節點內容仍可由 LLM 生成。 |

**湧現式協作**是先定角色、目標和互動規則，允許 Agent 在對話中自行提出想法、分工與修正；適合探索性工作，但路徑和成本較難事先預測。「湧現」不是正確性的保證。**顯式控制**則由開發者預先定義允許的狀態、轉移和停止條件；結果較容易重現與稽核，但規則若寫得太死，面對新情況需要修改圖。實務上可混用：讓模型在節點內提出方案，再用程式的條件邊和驗證器決定是否採納。[AutoGen 官方團隊說明](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)、[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)。

## 2. AutoGen 軟體團隊：動態回退、QA 與對話品質

### 2.1 需求變更時，如何立即回產品經理？

原教材的 RoundRobinGroupChat 依照成員列表輪流發言。若審查員剛發現需求改版，下一位仍由固定順序決定，因此它不適合表達「此時必須立刻回到產品經理」。改成 SelectorGroupChat 並提供確定性的 selector_func：

~~~mermaid
flowchart LR
    PM[產品經理確認需求版本] --> E[工程師提交候選版本]
    E --> R[審查員]
    R -->|需求變更 REQUIREMENTS_CHANGED| PM
    R -->|審查通過 REVIEW_PASS| Q[QA 執行測試]
    R -->|程式需修改| E
    Q -->|QA_FAIL 且未超過預算| E
    Q -->|QA_PASS| OK([完成])
    Q -->|修正次數或時間耗盡| H([求助人類])
~~~

路由的關鍵是**結構化事件、需求版本與最大輪次**。審查員不能只寫「我覺得不太對」；應回報 REQUIREMENTS_CHANGED 及新版本號。產品經理批准 v2 後，工程師提交的程式需標示 spec_version=2；QA 只能驗收目前核准版本。若已執行的測試對應 v1，版本變更後必須重新測試。系統設最多修正次數或時間上限，避免無限回退。[AutoGen 官方 SelectorGroupChat 說明](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html)。

[可執行的動態回退示範](../lab/dynamic_team_lab.py) 已使用真正的 SelectorGroupChat 和自訂 selector_func：審查員發出 REQUIREMENTS_CHANGED:v2 後，下一位確實是產品經理；其後由 QA 真正跑五項測試。執行指令：

~~~powershell
.venv\Scripts\python.exe -X utf8 -m lab.dynamic_team_lab
~~~

這個離線示範的 PM、Engineer、Reviewer 回覆仍來自預寫的 Replay 資料；**動態路由和 QA 程式測試是真的執行**，不能據此宣稱 LLM 自主辨識需求變更。示範用 QA 目前只測計算功能，尚未檢查測試結果的 spec_version 是否等於最新核准版本；前述版本一致性屬於正式實作還需補上的驗收條件。示範紀錄見 [dynamic_team.json](../outputs/dynamic_team.json)。

### 2.2 新增 Quality Assurance 角色

若建立一般 AssistantAgent，可用下列 system message 描述職責：

> 你是測試工程師。只處理目前經產品經理核准、審查員通過的程式版本。先執行正常值、邊界值與非法輸入測試；逐項報告實際值、預期值與失敗原因。只有測試程式真的回報全部通過，才能輸出 QA_PASS；否則輸出 QA_FAIL，附上可重現的案例，不得憑文字推測宣稱已測試。

**System Message 只是指令，不能自行執行測試。** 因此本專案在 [team_lab.py](../lab/team_lab.py) 加入程式型的 QualityAssurance Agent，呼叫 [energy.py](../lab/energy.py) 的 check_candidate()：驗證 1000 W×2 h=2 kWh、500 W×3 h=1.5 kWh、零功率，以及兩組負數必須被拒絕。第一版漏除以 1000，實測回傳 2000，QA_FAIL；第二版通過才 QA_PASS。停止訊號只接受 QA 發出。QA 仍需有測試品質，不能把「五項通過」誤當成涵蓋所有可能錯誤。

### 2.3 對話品質監控

監控程式每一輪記錄 task_id、需求版本、發言者、訊息、工具呼叫、實際測試結果與耗時。可訂以下規則：

| 偵測信號 | 例子 | 介入動作 |
|---|---|---|
| 離題 | 連續兩輪未產生需求、程式、審查或測試事件 | 提醒共同目標；仍離題則暫停交人工 |
| 循環 | 相同錯誤及相同候選版本重複兩次 | 禁止無改動的重試，要求不同修正方案或轉人工 |
| 版本不一致 | QA 正在測 v1，但產品經理已核准 v2 | 丟棄過期測試結果，回到工程師及 QA |
| 空口宣稱完成 | Agent 說「測試通過」，卻找不到測試執行紀錄 | 不接受完成訊號，要求測試工具的回傳值 |
| 預算超限 | 達到八次發言、指定時間或成本上限 | 標記 needs_help，保存對話與失敗原因 |

門檻只是設計示例，應依實際誤報率調整。監控器和終止條件要放在協作流程之外或作為獨立驗證元件，避免受被監控 Agent 的一句「完成」直接操控。

## 3. AgentScope 三國狼人殺：訊息、獵人與分散式挑戰

### 3.1 MsgHub 相較直接函式呼叫的價值

直接函式呼叫適合少數固定步驟，例如 moderator 依次呼叫 wolf()、witch()。MsgHub 更適合「目前這組成員都該收到訊息」的情況：開發者指定參與者，成員發言後由中心協助廣播；夜晚狼人可以組成私密群組，白天再切到公開群組，新增／移除參與者也較方便。[AgentScope 官方 Pipeline／MsgHub 文件](https://doc.agentscope.io/tutorial/task_pipeline.html)。

訊息結構也讓發送者、接收者、回合與內容比較容易記錄；fanout 可收集多名玩家的投票。不過 MsgHub **不會自動保證**跨伺服器的持久化、權限隔離或恰好一次送達。若要用在分散式環境，這些仍需額外設計。特別有價值的情境是玩家加入退出、不同階段改變訊息可見範圍，以及同時向多名玩家徵求決策。

### 3.2 新角色「獵人」的結構化輸出

**本題先定遊戲規則**：獵人被狼人擊殺或投票淘汰時可開一槍；被女巫毒死時不能開槍；全場只可開槍一次，且只能選另一名存活玩家。這是本解答的規則設定，其他狼人殺版本可能不同。

~~~python
from pydantic import BaseModel, Field, model_validator

class HunterAction(BaseModel):
    shoot: bool = Field(description="這次是否開槍")
    target_name: str | None = Field(default=None, description="目標玩家姓名")
    reason: str = Field(min_length=1, max_length=200, description="簡短理由")

    @model_validator(mode="after")
    def target_matches_choice(self):
        if self.shoot and not self.target_name:
            raise ValueError("開槍必須指定目標")
        if not self.shoot and self.target_name is not None:
            raise ValueError("不開槍時不可指定目標")
        return self
~~~

這個資料模型只能檢查**欄位及跨欄位關係**。主持人還必須讀權威遊戲狀態，確認死亡原因、目標仍存活、目標不是獵人自己、獵人未開過槍，並為死亡事件配置唯一 event_id，避免重送訊息時重複開槍。開槍結果應由主持人原子性地記錄並廣播，不能只相信 Agent 回覆。本專案提供 [可執行的 Pydantic 規則範例](../lab/hunter_rule_example.py)；它沒有導入或測試 AgentScope 的完整狼人殺遊戲。教材範例的 DiscussionModelCN 和 WitchActionModelCN 只列欄位，不能僅靠 bool 型別推論已滿足跨回合規則。[AgentScope 官方結構化輸出說明](https://doc.agentscope.io/tutorial/task_agent.html)。

### 3.3 分散式部署的技術挑戰

最危險的是**順序與權威狀態不一致**：狼人夜晚票尚未全部收到，女巫就看到錯誤的死亡目標；同一個獵人開槍事件因重試被處理兩次；跨伺服器延遲使玩家收到上一回合的廣播。可採每個遊戲房間由單一權威主持節點排序事件，訊息帶 game_id、round_id、phase、seq、event_id；所有狀態改動先寫事件紀錄並檢查版本，再對外廣播。接收端依 event_id 去重、依 seq 排序；晚到的舊階段訊息拒收。房間故障時從快照與事件日誌恢復，主節點切換需避免兩個主持人同時裁決。夜晚私訊另外做授權檢查，並設定投票逾時與斷線重連政策。這些屬於建議架構，不能因為框架支援部署就假設已自動完成。[AgentScope Runtime 官方說明](https://github.com/agentscope-ai/agentscope-runtime)。

## 4. CAMEL：完成分歧與 Workforce

### 4.1 兩位 Agent 對完成狀態意見不同

教材的判斷是：只要任一訊息含有 <CAMEL_TASK_DONE> 就結束。這容易把單方意見當成整體完成。可改成兩階段協議：

1. 一方提出 FINISH_PROPOSED，附已完成章節清單與證據；**暫不結束**。
2. 另一方回覆 AGREE、OBJECT（列出缺口）或 REQUEST_REVISION。
3. 只有雙方同意，且外部檢查器確認結構完整、引用可追溯、字數與章節達標，才由控制器輸出 FINAL_DONE。
4. 若有分歧，限定兩輪修改；之後交第三方審稿者或人類裁定。達到輪次／時間上限時保存草稿，標記 unresolved，而非假報完成。

這使完成訊號成為「提案」，最終結束由可檢查的條件決定；亦可保留教材既有標記作為相容的提案輸入，再由新的控制器判定是否真正完成。

### 4.2 最新 Workforce 與 AutoGen 群聊

CAMEL 的 [Workforce 官方文件](https://docs.camel-ai.org/key_modules/workforce) 說明：task_agent 拆解總任務，coordinator_agent 把子任務指派給合適的 worker；子任務可有依賴、可並行執行，失敗時有恢復決策。Worker 可以是單一 Agent，也能是由雙角色對談組成的 RolePlayingWorker。這已超出教材的雙角色逐輪對話。[官方資料結構說明](https://docs.camel-ai.org/key_modules/workforce)。

~~~mermaid
flowchart TD
    G[總任務：完成研究論文] --> T[task_agent 拆解任務]
    T --> C[coordinator_agent 指派]
    C --> A[文獻檢索 worker]
    C --> B[實驗設計 worker]
    A --> D[有依賴的寫作 worker]
    B --> D
    D --> E{結果檢查}
    E -->|失敗| C
    E -->|通過| F([彙整完成])
~~~

對比教材中的 AutoGen RoundRobinGroupChat：它把參與者放在一個共用對話裡，依固定順序輪流發言；CAMEL Workforce 的重點是**任務拆解、指派、依賴與工作者結果**。但這不是兩框架功能的排他界線：AutoGen 也提供 SelectorGroupChat 等更動態的團隊方式，CAMEL 也能讓 worker 內部採對話。差異是此處所比較的兩種**具體編排模式**。本專案沒有安裝與實測 Workforce。[AutoGen SelectorGroupChat 官方文件](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html)。

## 5. LangGraph：基本圖、反思回圈與更複雜流程

### 5.1 教材的三步問答

~~~mermaid
flowchart LR
    S([START]) --> U[understand 理解問題]
    U --> R[search 搜尋資料]
    R --> A[answer 形成回答]
    A --> E([END])
~~~

共享 SearchState 包含問題、搜尋詞、搜尋結果、最終答案及目前步驟等欄位。上圖**只有普通邊，沒有品質條件邊**；教材的回答節點雖會依搜尋成功或失敗採不同文字策略，那是節點內判斷，圖的路線仍是 understand → search → answer → END。執行完不代表答案已通過品質驗收。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)。

### 5.2 加入反思節點與有限循環

~~~mermaid
flowchart TD
    S([START]) --> U[understand]
    U --> R[search]
    R --> A[answer]
    A --> F[reflect：檢查長度、細節、來源和錯誤]
    F -->|足夠且有依據| E([END：pass])
    F -->|來源不足且可重試| R
    F -->|只有表達太短且可重試| A
    F -->|重試耗盡或無資料| H([END：needs_help])
~~~

State 增加 answer、feedback、search_attempts、answer_attempts、max_retries、status 等欄位。條件邊的路由邏輯可以寫成：

~~~text
if 無搜尋錯誤且答案有足夠內容、細節與來源支持 → END(pass)
elif 缺來源且 search_attempts < 搜尋預算 → search
elif 資料夠但表達過短且 answer_attempts < 生成預算 → answer
else → END(needs_help)
~~~

重新生成前把具體 feedback（例如「缺少數值例子」）放進 State，否則以完全相同輸入重跑容易得到同樣的結果。長度只是粗略訊號，長答案也可能錯；需要來源支持檢查或人工抽查。本專案的 [離線 LangGraph 實驗](../lab/graph_lab.py) 已實際加入 reflect、條件邊與有限重試，但它目前主要以**有效教材片段數**作為教學用門檻，沒有完整實作上圖的「答案太短就回 answer」支線。兩片段來自同一本教材，不是兩個獨立來源。

### 5.3 更複雜的「產生程式—測試—修正」循環

~~~mermaid
flowchart TD
    S([START]) --> Q[定義需求與驗收案例]
    Q --> G[產生候選程式]
    G --> X[靜態檢查及沙箱執行測試]
    X --> V{驗收與錯誤分類}
    V -->|全部通過| R[人工／審查節點]
    R -->|核准| E([END：交付])
    R -->|拒絕且可改| F[整理回饋]
    V -->|測試失敗且可改| F
    F --> G
    V -->|預算耗盡或不安全| H([END：needs_help])
    R -->|預算耗盡| H
~~~

State 應記錄 requirement_version、candidate_version、測試案例、測試結果、失敗原因、修正次數、人工決定及每一步的證據。G 只產生候選；X 真的執行測試（執行環境應隔離並限權）；V 由結果分類下一步；F 把失敗回饋給 G；R 擋住未經核准的交付。需求版本若改變，舊測試結果作廢。另設最大修正次數與整體逾時，避免無限迴圈。LangGraph 的條件邊、持久化與 interrupt 可支援這類設計，但持久化和審核紀錄的可靠性仍取決於實際儲存系統與應用配置。[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[人工中斷與恢復](https://docs.langchain.com/oss/python/langgraph/interrupts)。

## 6. 三個產品的框架選型

| 產品 | 首選 | 理由與必要補充 |
|---|---|---|
| A 高併發客服 | **AgentScope** | 需要多會話狀態、工具與部署相關能力，AgentScope 的元件與 Runtime 方向相符。但「每秒 1000+、低於 2 秒、24/7」是**整套服務的量測目標**，不能由選框架保證。需將簡單問題先用 FAQ／快取處理，複雜問題再送 Agent；配合非同步服務、模型推論容量、負載平衡、擴縮、逾時降級、可觀測性與壓測。若實際只是固定 FAQ，簡單服務也可能比 Agent 框架合適。[AgentScope Runtime](https://github.com/agentscope-ai/agentscope-runtime) |
| B 論文輔助寫作 | **CAMEL Workforce** | 研究員與寫作員可以深度討論；進一步將文獻蒐集、實驗設計、資料分析、撰稿拆成有依賴的任務，分配給專長 worker；某項 worker 內可使用 RolePlayingWorker。必須另加來源核對、引用管理、實驗結果驗證及人工學術審閱。若只需兩個角色單純對談，教材的 CAMEL RolePlaying 已足夠。[Workforce 文件](https://docs.camel-ai.org/key_modules/workforce) |
| C 金融風控審批 | **LangGraph** | 審核→風險→額度→合規→人工→最終決策的次序、條件分支、失敗重試與人工中斷都可明確建模。每個節點應保留輸入、規則版本、輸出、操作者與時間；規則計算和最終核准由受控程式與授權人員負責，模型只提出可審查的輔助資訊。正式的不可竄改稽核紀錄、身份權限、法規符合性與資料保護必須由周邊系統另外實作和驗證，不能因有圖與 checkpoint 就假設完成。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) |

**選型的判準**：先看任務的主要不確定性在哪裡。A 的瓶頸是整體服務容量和延遲；B 需要自主分工與內容品質檢核；C 首重確定的分支、版本與可追溯的人工決定。以上是架構建議，並非效能基準測試或已完成部署的結果。

# 教師解答與現場提示

先讓同學預測，再展示答案。

## A：原版與反思版

| 版本 | attempts | 來源片段 | status | 原因 |
|---|---:|---:|---|---|
| baseline | 1 | 1 | unreviewed | 固定三步結束，沒有品質檢查 |
| reflection | 2 | 2 | pass | 第一輪不足，第二輪補足 |

反思版 trace：understand → search#1:hits=1 → answer → reflect:retry → search#2:hits=2 → answer → reflect:pass。

## B：條件邊

~~~python
def choose_next(status):
    return 'search' if status == 'retry' else 'end'
~~~

完整參考檔在 solutions/policy_solution.py。再把此函式接入 graph_lab.py 的 route_after_reflection，才有測到真實 LangGraph 的路由。needs_help 一定要結束；不能所有「不是 pass」都回 search。

常見錯誤：寫 if status == 'pass': return 'end'，else 一律 search。這會讓重試次數已耗盡的 needs_help 仍往回走，最後可能撞上 recursion_limit。邏輯上的重試預算是第一道限制，框架步數限制是最後一道防護。

## C：門檻與預算

| 試驗 | 搜尋次數 | 結果 | 理由 |
|---|---:|---|---|
| C1：1／1 | 1 | pass | 第一輪已達一筆來源片段 |
| C2：2／0 | 1 | needs_help | 不足兩筆且不能重試 |
| C3：3／1 | 2 | needs_help | 資料庫只有兩筆，再搜尋也湊不到三筆 |

MAX_RETRIES 計的是「第一次之外額外允許幾次」，所以最大 attempts 是 1 + MAX_RETRIES。

## D：故障

- transient：第一次 error、第二次兩筆，pass。
- failure：兩次 error，needs_help。
- 天氣：兩次零筆，needs_help。

不可用固定知識輸出冒充今天的網路查詢。工具沒有資料時清楚回報，是功能的一部分。

## E：QA

正確式子是 power_w * hours / 1000。還要拒絕負功率與負時間，這是本實驗的領域規則；不表示所有電力情境都禁止負功率，因為這裡定義的是「非負負載用電量計算器」。

第一輪 buggy 會在 1000×2、500×3、兩個負值案例失敗；0×2 原本就對。第二輪 fixed 五項通過。新加 250×4=1 後共六項，成功文字也應相應更新。

Replay 是固定回覆替身。即使提示詞叫 Engineer 修正，它也不會依 QA 動態推理；第二個回覆是我們事先排好的。教學價值在於可重現地驗證「錯誤是否被 QA 看見、修正結果是否再被測試」。

## 四框架討論題參考

- AutoGen：多角色對話，但可由程式限制順序與結束。
- AgentScope：先思考訊息誰能看到；型別規則還不夠，需要場景驗證。
- CAMEL：角色＋共同目標＋互動規範；意見不合需仲裁與截止條件。
- LangGraph：明確定義狀態、節點與分支，適合示範可觀察的循環。

沒有唯一正確的品牌選擇。要求同學說出「需求 → 設計理由 → 驗證方式」就比背產品名稱有價值。

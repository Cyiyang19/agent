# CH6 框架開發實踐：讓 Agent 的工作可以組合、觀察與驗證

教材：Hello-Agents V1.0.2，第六章 6.1–6.6（PDF 150–182 頁）。閱讀方式：先看流程，再看 Python 名稱，最後做實驗。

## 本節課結束應該會什麼？

1. 用一句話區分 AutoGen、AgentScope、CAMEL、LangGraph。
2. 在程式裡指出 State、Node、Edge。
3. 修改品質門檻，預測並驗證路徑如何改變。
4. 分辨「模型提出結果」「測試真的執行」「品質條件通過」。

## 6.1 為什麼要框架？

先想像你用 Python 寫了「呼叫模型 → 搜尋 → 回答」。接著老師要加第二個角色、錯誤重試、歷史訊息、記錄每一步，程式很快到處都是重複的控制邏輯。

框架把大家常用的流程管理、訊息傳遞與元件介面整理好。你仍要決定任務、工具、資料、驗收標準。**框架管理流程，不替你保證答案正確。**

| 關注點 | 我們要回答的問題 | 本實驗位置 |
|---|---|---|
| 模型 | 回覆從哪裡來？ | AutoGen Replay 測試資料 |
| 工具 | 真的做什麼？ | local_search_node、check_candidate |
| 狀態 | 現在知道什麼、試了幾次？ | SearchState |
| 控制 | 下一步去哪、什麼時候停？ | 條件邊、終止條件 |
| 觀察 | 有哪些執行證據？ | trace、JSON、pytest |

### 四種框架的閱讀地圖

| 框架 | 直覺 | 教材案例 | 常見設計重點 | 代價／限制 |
|---|---|---|---|---|
| AutoGen | 組一個可以輪流工作的團隊 | 軟體開發團隊 | 角色、訊息、輪流／選擇發言與停止 | 對話增加成本；角色說完成仍需驗證 |
| AgentScope | 管好大家的訊息與協作 | 三國狼人殺 | Msg、MsgHub、並行操作與結構化輸出 | 要額外管理狀態、權限與錯誤 |
| CAMEL | 讓兩個角色相互提出要求並回覆 | 心理學家與作家寫書 | RolePlaying、角色提示與共享目標 | 可能離題、互相附和或無法結束 |
| LangGraph | 把執行流程畫成可跑的圖 | 理解／搜尋／回答 | State、Node、Edge、分支與循環 | 需自己設計狀態與路由，節點仍可能出錯 |

這是教材代表性用法，不是功能排他清單。AutoGen 可以控制流程，LangGraph 也可以建多智能體；不要把比較表當成「其他框架做不到」。

## 6.2 AutoGen：對話協作與真正的 QA

教材使用 AutoGen 0.7.4，本專案也固定這個版本；不把書中「最新版本」當成今天的現況。

~~~mermaid
flowchart LR
    P[ProductManager 定驗收] --> E[Engineer 選候選實作]
    E --> R[CodeReviewer 看問題]
    R --> Q[QualityAssurance 實際測試]
    Q -->|QA_FAIL 且還有輪次| P
    Q -->|QA_PASS 或輪次耗盡| S[停止並回報狀態]
~~~

- AssistantAgent：以模型客戶端與系統訊息定義助理角色。
- RoundRobinGroupChat：依參與者順序輪流發言。
- TextMentionTermination：偵測停止文字；本例只接受 QA 來源的 TERMINATE。
- max_turns：即使永遠沒人說成功，也必須停止。
- async／await：允許非同步操作；**不表示這個輪流團隊的四個角色同時執行。**

### 本次修改了什麼？

原例是比特幣價格應用，本次改為可驗證的用電量計算。先算：

~~~text
能量 Wh = 功率 W × 時間 h
1 kWh = 1000 Wh
所以：1000 W × 2 h ÷ 1000 = 2 kWh
~~~

原例的 UserProxyAgent 是人類輸入介面；單靠 description 寫「執行測試」，不會自動變出測試執行器。本次加入真正的 QA 類別，呼叫五個檢查案例。

離線 Engineer 第一輪選 buggy，第二輪選 fixed。兩個函式由教材改編者事先提供，沒有讓模型產生任意程式後執行。**這證明團隊流程與 QA 可以運作，不證明模型能自己寫程式或修錯。**

### Demo 5 看哪三行？

~~~text
Engineer: {"implementation":"buggy"}
QualityAssurance: QA_FAIL: ... expected 2 kWh, got 2000 ...
QualityAssurance: QA_PASS: fixed; 5 executable checks passed. TERMINATE
~~~

如果改成選單 6，Engineer 一直選錯，就會在 8 次角色發言的上限結束；結果是 needs_help，不是成功。

**提問：** 輪詢流程中 QA 失敗後，會直接跳到 Engineer 嗎？不會。這個版本仍按 PM → Engineer → Reviewer → QA；若要直接回退須另外設計路由／選擇機制。

## 6.3 AgentScope：誰可以收到哪個訊息？

教材案例是三國狼人殺。它的價值不是遊戲本身，而是不同階段有不同的訊息可見範圍。

~~~mermaid
flowchart TB
    H[主持人控制遊戲階段] --> W[夜晚：狼人私密群組]
    H --> A[白天：全員公開討論]
    H --> V[投票：並行收集個別決定]
~~~

Msg 表示訊息；MsgHub 協助群組內訊息廣播；fanout 類型的操作可向多個角色發出任務並收集回覆。

**班級小活動（2 分鐘）：** A、B 是狼人，C、D 是村民。A 說「今晚選 C」，誰應該收到？在夜晚狼人群組裡只有 B 與需要知情的主持流程；不該廣播給 C、D。請同學畫出訊息邊界。

### 結構化輸出不是規則正確的充分條件

設定 use_antidote、use_poison 都是 bool，只保證型別；不會自動保證藥只用一次、目標還活著、同一回合合法。必須在驗證器或遊戲控制邏輯檢查跨欄位與跨回合限制。

同樣地，MsgHub 的群組抽象不等於已經完成跨伺服器可靠通訊、權限隔離或持久化。這些要依版本與部署設計驗證。**本課沒有執行 AgentScope 的多人遊戲或分散式部署。**

## 6.4 CAMEL：角色扮演與共同任務

教材的例子是心理學家與作家協作寫科普電子書。

~~~mermaid
flowchart LR
    T[共同目標：寫一份科普內容] --> U[AI User 作家提出要求]
    U --> A[AI Assistant 心理學家回覆]
    A --> U
    A --> F[完成訊號與輪次上限]
~~~

AI User 是扮演提需求角色的 AI，**不是坐在電腦前的人**。Inception prompting 是在開始時交代雙方角色、目標與行為規範。

**班級小活動（2 分鐘）：** 改成「電機研究員＋科普作者」。共同目標是用 150 字教高中生 kW 與 kWh 的差別；提出兩條驗收標準，例如包含單位換算、包含 1000 W／2 h 的例子。

只看到完成標記不代表內容正確。如果兩者意見不同，應先用共同規則檢查，必要時交由人工；到達輪次上限就停，不讓對話一直互相說「很棒」。本次不執行 CAMEL，也不宣稱比較出哪個框架輸出最好。

## 6.5 LangGraph：State、Node、Edge

先用生活例子：做實驗的紀錄表是 State，每個實驗步驟是 Node，決定下一步的箭頭是 Edge。

### 原本的三步流程

~~~mermaid
flowchart LR
    S([START]) --> U[understand]
    U --> R[search]
    R --> A[answer]
    A --> E([END])
~~~

這個流程有跑到最後，不代表答案夠完整。原教材也處理了搜尋例外，但主圖沒有額外的反思回圈。

### 改編後的品質檢查與重試

~~~mermaid
flowchart TD
    S([START]) --> U[understand：找主題]
    U --> R[search：取教材資料]
    R --> A[answer：產生含來源的答案]
    A --> F[reflect：檢查有效來源數]
    F -->|來源足夠：pass| E([END])
    F -->|不足且還有預算：retry| R
    F -->|預算耗盡：needs_help| E
~~~

| 名稱 | 意思 | 看程式時找什麼 |
|---|---|---|
| State | 整個流程共享的資料 | question、search_results、attempts、status |
| Node | 讀狀態、回傳局部更新的函式 | local_search_node、reflect_node |
| Edge | 接下去執行的方向 | add_edge |
| Conditional edge | 根據狀態選方向 | add_conditional_edges |
| Reducer | 合併多次狀態更新的方法 | trace 用 operator.add 累加 |
| compile | 把圖定義變成可執行物件 | workflow.compile() |
| invoke | 實際執行一次流程 | app.invoke(initial_state) |

### 三段關鍵程式

~~~python
# 1. node 只回傳要更新的欄位
return {'search_results': found, 'attempts': attempt}

# 2. 是否還能重試？第一次搜尋不算重試
retry = state['attempts'] < 1 + state['max_retries']

# 3. status 決定圖上的方向
return 'search' if state['status'] == 'retry' else 'end'
~~~

MAX_RETRIES = 1，代表最多兩次搜尋：第一次＋一次重試。若每次 LLM／工具呼叫需要付費或耗時，有限重試同時控制時間與成本。

### 改編的品質標準與界線

本次 pass 的意思是：無搜尋錯誤，且答案包含至少 MIN_SOURCES 個本次查到的不重複教材片段 ID。兩個片段來自同一本教材，**不是兩個獨立出版來源**。

這只是教學用的代理指標。來源數多不一定正確；程式仍未驗證來源真實性、文本是否真的支持主張、或答案是否回答完整。正式應用應加入任務專屬測試與人工抽查。

## 6.6 怎麼選框架？

先問「誰決定下一步？」再問「怎麼驗證結果？」

- 想呈現角色互相討論：先考慮 AutoGen 或 CAMEL 的協作方式。
- 需要訊息分發、群組與多角色互動：研究 AgentScope 的元件與版本能力。
- 有清楚的步驟、分支和重試條件：LangGraph 的圖比較直接。
- 只是很短的固定腳本：原生 Python 也可能足夠。

這些是教材情境的選型理由，不是性能測試排名。框架本身不保證每秒千次請求或固定延遲。

### 下課前自測

1. 寫 JSON schema 就能防止所有違反遊戲規則的行為嗎？
2. 把重試次數加到 100，是否就能回答不存在於資料庫的問題？
3. AutoGen 說 TERMINATE，是否一定表示程式測試成功？
4. 本次 demo 有驗證 LLM 的推理能力嗎？

答案：1 否，還需規則驗證；2 否；3 否，本例額外綁定 QA 與實測；4 沒有，驗證的是框架與控制邏輯。
